# DDR200 for Hekate

The driver tracks DDR200 at 199.68 MHz and 166.40 MHz. The test setup uses
a Samsung PRO Plus, HOS 21.2.0, Atmosphère 1.12.2 and Hekate 6.5.5.
The upstream FS tables cover HOS through 23.5.0.

Build with devkitA64 and generate the KIPM.

```sh
make clean
make -j4 EXTRA_DEFINES='-DEMUMMC_DDR200_PERF_TRIAL -DEMUMMC_DDR200_READ_AHEAD -DEMUMMC_DDR200_COUNTED_READS -DEMUMMC_DDR200_ADMA_PROBE'
python3 tools/package-build.py
```

Hekate injects `bootloader/sys/emummc.kipm` when an emuMMC entry
launches `pkg3=atmosphere/package3`. Use `emummcforce=1` on that entry.
Back up the previous KIPM before copying the new one into place.

## Runtime policy

Initial DDR200 qualification requires an eight-tap window. After it qualifies,
the driver sweeps within 16 taps of the previous eye's center after native
handoff, 64 MiB of I/O, or 500 ms of busy time. The intersection of up to
three measured windows supplies candidate taps. Full-rate runtime tuning
prefers the low side to leave room for a collapsing right edge.

A five- or six-tap full-rate eye can continue with two taps of margin if two
256 KiB reads at distinct passing taps agree. The driver rechecks these
narrow windows every 32 MiB or 250 ms of busy time. Wider eyes and reduced
DDR200 use a three-tap guard. The secondary data read also uses that guard
when another guarded tap is available. An eight-tap eye has two guarded
taps, so both can be verified at full margin. Failed verification triggers
normal fallback.
An unchanged narrow eye can keep its verified tap for up to two seconds
while sweeps continue. A fresh native CMD6 handoff starts a new sweep
history because the earlier samples were taken on a different link setup.

The release clock uses PLLC4_OUT0 at 998.4 MHz, the SDMMC1 source divider
of 2.5, and the SDHCI divider of 2, giving 199.68 MHz.
The performance build checks and selects
the card's Type A driver strength as part of the SDR12-to-DDR200 switch
when the card advertises it and accepts it in CMD6 CHECK. The report gives
actual selected strength and separates DMA wait from total command time
for successful reads of at least 256 KiB at 199.68 MHz. It also records
what fraction of those reads needed a bounce buffer.
The optional `EMUMMC_DDR200_DRIVE_C` trial checks Type C first and uses
the existing Type A negotiation if the card rejects Type C.
The optional `EMUMMC_DDR200_COUNTED_READS` trial uses Auto CMD23 for large
full-rate reads when the card advertises CMD23 and SDHCI is in v4 mode
with 64-bit DMA. The first failed counted read restores Auto CMD12 for
the rest of the boot. The trace reports how many counted reads completed.

The ADMA2 build batches sequential filesystem reads of 64 KiB or more
into a private 2 MiB DMA window after observing 512 KiB of adjacent
requests at full rate. The controller must advertise ADMA2 and be in
64-bit SDHCI v4 mode. Read-ahead requires two taps with at least three
taps of margin in eyes of eight or more taps. In six- and seven-tap eyes
it requires two taps with at least two taps of margin.

Both taps must return 2 MiB matching the same sectors read in 256 KiB
SDMA slices. The reference uses a 512 KiB-aligned address so every slice
finishes before any boundary restart. Each batch uses ADMA2. The driver
rechecks the pair when a tap leaves its guarded range, the active tap
changes to an unverified one, full rate is restored after a slowdown, or
the DMA mapping is reset. A failed fill disables read-ahead until the next
boot. Overlapping writes, eject and native controller transitions
invalidate cached sectors. The trace preserves the latest qualification,
DMA progress on the last failed read, and total ADMA2 traffic and speed.

The older SDMA read-ahead option, built without `EMUMMC_DDR200_ADMA_PROBE`,
requires nine passing taps and filesystem requests of at least 256 KiB.

The driver first repairs a failed data command with explicit CMD12, waits
for CMD13 transfer state and READY_FOR_DATA, and resets CMD/DAT. Read recovery
tries new taps at the current clock, then validated DDR200 at 166.40 MHz,
then standard SDR104 timing. SDR104 uses the serialized emuMMC transport.
An ambiguous protocol switch or failed stop returns a storage error. A failed
write can have programmed some blocks, so the caller receives its error after
link recovery. At a degraded rate the driver schedules up to six full-rate
retries with a 5–300 second backoff after idle or enough traffic. The trace
marks the boot as unstable if it needed to leave full rate.
Writes use a verified lower rate when the full-rate eye is narrow.
The upgrade policy waits at least five seconds after the last write.

After the boot power window closes, Horizon owns SD power. At the native
eMMC close, the driver verifies SDR104 before handing back the SD link and
runs the paired SD close with the emuMMC locks released. On a cold access
it checks the power GPIO and pinmux and yields the locks while Horizon
restores power. Wake can restore the host's SDR104 setup while the card
retains DDR200. The driver checks for an SDR104 CMD6 reply. If it cannot
confirm SDR104 it verifies the retained link at 166.40 MHz before attempting
to restore the previous DDR200 rate. Both wake paths preserve DMA scratch.

## Matrix

Build with `EXTRA_DEFINES=-DEMUMMC_DDR200_MATRIX` to produce a separate
diagnostic KIPM for the same Hekate path.

The diagnostic boots with the release runtime policy. Its first step runs
on a normal SD filesystem request at least 20 seconds after the first
successful native DDR200 handoff. Upcoming requests advance the experiment.
Hold Volume Down by itself for three seconds to skip or end it.
It compares five repeated scans per clock, gating
between tap samples versus leaving the clock on, and the 0, 10 and 100 ms
settling targets after a confirmed DDR200 switch. The report measures each
settling scan's start relative to the switch. Later scans may start after
their target as earlier scans finish.

The diagnostic reads 64 MiB in 2 MiB slices at each clock, sweeps every
8 MiB and again after idle, and times up to 256 MiB of sequential reads at
each clock. It logs the card's driver strength and power limits from CMD6
and tests advertised standard driver strengths. It runs the CMD6 changes
after the read comparisons. Each step uses the caller's storage locks and a
250 ms command budget. The next request after an idle interval captures the
idle sweep. The report identifies shortened load tests and idle
periods if the system keeps using the card. Matching reads protect the
normal profile while the experiment changes clocks.

The trace holds 40 experimental records and eight recent runtime records in
matrix mode. The ADMA2 test reserves eight of the 48 records for DMA results.
Each sweep includes the sampled eye, applied tap, elapsed microseconds, bytes
transferred since reassertion, rate and driver strength. It also records
actual clock registers, CMD12/CMD13 cleanup, profile transitions and timed
throughput. The logs can show whether contraction correlates with load and
whether the eye recovers after idle. A physical measurement is needed to
attribute a reversible change to heat or rail droop.

## Console test

1. Open Hekate **Launch** and select **CFW on emuMMC (DDR200)**.
2. Run SDBench and record the 2, 4 and 8 MiB read results and writes.
3. Run three sleep/wake cycles and benchmark after each.
4. Hold **Volume + and Volume −** together for three seconds to save the
   report, then reconnect in SD UMS and collect it from
   `atmosphere/fatal_errors`.

Use `python3 tools/read-ddr-trace.py report_*.bin` to decode the reports.
Use `sh tests/run.sh` for the ASan and UBSan checks. They exercise eye drift,
read verification, command cleanup after a DMA timeout, the matrix schedule,
suspend/wake and read batching. Console testing measures sustained
throughput at the observed tap window, as well as sleep/wake.
