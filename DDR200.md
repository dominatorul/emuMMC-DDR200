# DDR200 for Hekate

The default build targets DDR200 at 199.68 MHz and falls back to SDR104. The test setup uses
a Samsung PRO Plus, HOS 21.2.0, Atmosphère 1.12.2 and Hekate 6.5.5.
The upstream FS tables cover HOS through 23.5.0.

Build with devkitA64 and generate the KIPM.

```sh
make clean
make -j4
python3 tools/package-build.py
```

Hekate injects `bootloader/sys/emummc.kipm` when an emuMMC entry
launches `pkg3=atmosphere/package3`. Use `emummcforce=1` on that entry.
Back up the previous KIPM before copying the new one into place.

## Runtime policy

Initial DDR200 qualification centers the widest complete CMD19 pass window,
following Hekate, and requires at least eight passing taps. After it qualifies,
the driver sweeps within 16 taps of the previous eye's center after native
handoff, 64 MiB of I/O, or 500 ms of busy time. The intersection of up to
three measured windows supplies candidate taps. Full-rate runtime tuning
prefers the low side to leave room for a collapsing right edge. When the
local sweep clips an edge and must expand, the full sweep chooses the window
nearest the previous center. A new link with no history starts from the
widest passing window.

A five- or six-tap full-rate eye can continue with two taps of margin if two
256 KiB reads at distinct passing taps agree. The driver rechecks these
narrow windows every 32 MiB or 250 ms of busy time. Wider eyes and reduced
DDR200 use a three-tap guard. The secondary data read also uses that guard
when another guarded tap is available. An eight-tap eye has two guarded
taps, so both can be verified at full margin. Failed verification triggers
normal fallback.
An unchanged narrow eye can keep its verified tap for up to two seconds
while sweeps continue. A fresh native CMD6 handoff starts a new sweep
history because the earlier samples were taken on a different link setup.

The first five- to seven-tap runtime eye can trigger one calibration of the
host's 1.8 V pads per boot. This uses the existing SDMMC1 calibration values
while the link is idle and outside the wake sequence. A window of eight
taps or more must overlap across two consecutive scans and pass fresh data
verification before the driver installs a tap. The trace records the eye
before and after calibration even if later sweeps replace the scan history.

The release clock uses PLLC4_OUT0 at 998.4 MHz, the SDMMC1 source divider
of 2.5, and the SDHCI divider of 2, giving 199.68 MHz.
The performance build checks and selects
the card's Type A driver strength as part of the SDR12-to-DDR200 switch
when the card advertises it and accepts it in CMD6 CHECK. The report gives
actual selected strength and separates DMA wait from total command time
for successful reads of at least 256 KiB at 199.68 MHz. It also records
what fraction of those reads needed a bounce buffer.
The optional `EMUMMC_DDR200_DRIVE_C` trial checks Type C first and uses
the existing Type A negotiation if the card rejects Type C.
The optional `EMUMMC_DDR200_COUNTED_READS` trial uses Auto CMD23 for large
full-rate reads when the card advertises CMD23 and SDHCI is in v4 mode
with 64-bit DMA. The first failed counted read restores Auto CMD12 for
the rest of the boot. The trace reports how many counted reads completed.

With `EMUMMC_DDR200_ADMA_PROBE`, ordinary emuMMC SD data commands use ADMA2
on a controller that advertises it. This covers direct and bounce buffers,
writes, and the 256 KiB data checks used during runtime tuning. Hardware
CMD19 samples use SDHCI's buffer-ready tuning sequence with DMA disabled.
The driver maps a static descriptor page into the SD device address space
and uses the existing FS mappings for data. Each descriptor carries up to
65,024 bytes because Tegra210 rejects the zero-length encoding for 64 KiB.
Ordinary commands transfer up to 2 MiB per chain. SDMA remains available
when the controller lacks ADMA2 and during the native SD handoff.

The default build leaves read-ahead disabled. The optional legacy
`EMUMMC_DDR200_READ_AHEAD` build uses one 2 MiB data buffer and tracks four interleaved sector
streams. A request of at least 64 KiB can start a stream. Adjacent requests,
including smaller ones in a recognized stream, qualify after 512 KiB of
run-in. Both guarded taps must return matching 2 MiB ADMA2 reads before the
driver serves cached data. It requires three taps of margin in eyes of
eight or more taps, and two in six- and seven-tap eyes. It rechecks the
pair after a clock upgrade, reset or change in the guarded taps. A failed
fill disables speculation until the next boot. Overlapping writes, eject
and native controller transitions invalidate cached sectors.

With read-ahead enabled, the trace counts refusal reasons and reports the
fraction of recognized sequential bytes served from 2 MiB fills. It records SDMA restarts for all
emuMMC SD commands and retains the last eight failures with command,
tap, actual block count, DMA buffer offset within 512 KiB, and DMA progress.
For ADMA2, progress is the number of whole descriptors covered by the
controller's completed block count.

The older SDMA read-ahead option, built without `EMUMMC_DDR200_ADMA_PROBE`,
requires nine passing taps and filesystem requests of at least 256 KiB.

The driver first repairs a failed data command with explicit CMD12, waits
for CMD13 transfer state and READY_FOR_DATA, and resets CMD/DAT. Full-rate
recovery checks at least three distinct passing taps before dropping the
clock when the eye and recovery budget allow it. Repeated data failures
exclude previously failed taps across each request's retries. The runtime
fallback selects SDR104 with a checked CMD6 reply, hardware tuning and
CMD13 readiness. The trace records the reason for each clock drop. The
matrix can still measure 166.40 MHz as an experimental rate.
An ambiguous protocol switch or failed stop returns a storage error. A failed
write can have programmed some blocks, so the caller receives its error after
link recovery. At a degraded rate the driver schedules up to six full-rate
retries with a 5–300 second backoff after idle or enough traffic. The trace
marks the boot as unstable if it needed to leave full rate.
Writes can stay at 199.68 MHz on a six-tap eye with two verified taps at
two taps of margin. Writes with insufficient margin use SDR104.
The upgrade policy waits at least five seconds after the last write.

After the boot power window closes, Horizon owns SD power. At the native
eMMC close, the driver verifies SDR104 before handing back the SD link and
runs the paired SD close with the emuMMC locks released. On a cold access
it checks the power GPIO and pinmux and yields the locks while Horizon
restores power. Wake can restore the host's SDR104 setup while the card
retains DDR200. The driver checks for an SDR104 CMD6 reply. If it cannot
confirm SDR104, it restores and verifies the retained link at its requested
DDR200 rate. If DDR200 verification fails with a known link configuration,
the driver attempts a checked SDR104 switch and schedules the normal
full-rate retry. Both wake paths preserve DMA scratch.
The native handback and wake negotiation use SDMA with Horizon's existing
buffers, including the wake verification reads. The driver releases its
descriptor page after handback and before the paired
native close. After wake negotiation succeeds, the next ordinary data
command maps a fresh descriptor page. Trace version 25 keeps lifecycle
counts and descriptor map and unmap results alongside the runtime trace.

## Matrix

Build with `EXTRA_DEFINES=-DEMUMMC_DDR200_MATRIX` to produce a separate
diagnostic KIPM for the same Hekate path.

The diagnostic boots with the release runtime policy. Its first step runs
on a normal SD filesystem request at least 20 seconds after the first
successful native DDR200 handoff. Upcoming requests advance the experiment.
Hold Volume Down by itself for three seconds to skip or end it.
It compares five repeated scans per clock, gating
between tap samples versus leaving the clock on, and the 0, 10 and 100 ms
settling targets after a confirmed DDR200 switch. The report measures each
settling scan's start relative to the switch. Later scans may start after
their target as earlier scans finish.

The diagnostic reads 64 MiB in 2 MiB slices at each clock, sweeps every
8 MiB and again after idle, and times up to 256 MiB of sequential reads at
each clock. It logs the card's driver strength and power limits from CMD6
and tests advertised standard driver strengths. It runs the CMD6 changes
after the read comparisons. Each step uses the caller's storage locks and a
250 ms command budget. The next request after an idle interval captures the
idle sweep. The report identifies shortened load tests and idle
periods if the system keeps using the card. Matching reads protect the
normal profile while the experiment changes clocks.

The trace holds 40 experimental records and eight recent runtime records in
matrix mode. The full ADMA2 build reserves 23 of the 48 records for DMA
results, coverage and clock transitions.
Each sweep includes the sampled eye, applied tap, elapsed microseconds, bytes
transferred since reassertion, rate and driver strength. It also records
actual clock registers, CMD12/CMD13 cleanup, profile transitions and timed
throughput. The logs can show whether contraction correlates with load and
whether the eye recovers after idle. A physical measurement is needed to
attribute a reversible change to heat or rail droop.

## Console test

1. Open Hekate **Launch** and select **CFW on emuMMC (DDR200)**.
2. Run SDBench 1.1.4 to completion and record the read and write results.
3. Run three sleep/wake cycles and benchmark after each.
4. Hold **Volume + and Volume −** together for three seconds, then release both to save the
   report, then reconnect in SD UMS and collect it from
   `atmosphere/fatal_errors`.

Use `python3 tools/read-ddr-trace.py report_*.bin` to decode the reports.
Check the total SDMA restart counter, sequential coverage, CMD25 failures
and clock-drop reasons. Use `sh tests/run.sh` for ASan and UBSan checks of
descriptor chains, DMA error handling, tap retries, batching and lifecycle.

Report `14a3626e` captured a 2 MiB CMD18 at 199.68 MHz on tap 32 in the
29–36 window. SDMA hit a CRC error after its first software boundary restart
with 3,078 blocks left. The same sectors passed via ADMA2 at taps 32 and
33 with zero restarts. Across `14a3626e` and `a165f63`, 158 ADMA2 fills
passed and command throughput was 150–152 MB/s. These measurements isolate
a failure seen with the SDMA restart path. The new build uses ADMA2 for
ordinary SD data transfers as well, so the next trace can show any errors
that persist when the driver no longer restarts SDMA at 512 KiB boundaries.

## Wake recovery and diagnostic builds

Three `3d29f7a` reports captured after the sleep tests ended in link
reassertion. The failing CMD6 check used SDMA with zero boundary restarts.
No ordinary post-wake transfer followed the terminal reassertion in any of
the three reports. The new breadcrumbs record PLLC4 and report clock setup,
CMD13 readiness, and eye/data verification separately for each retained
link attempt. In `46fa899`, Horizon restored locked PLLC4 with DIVN/DIVM
52/2. The previous driver required 104/4 and refused to configure either
DDR200 rate. Both ratios give the same 998.4 MHz PLL output at 38.4 MHz.
The driver now checks the ratio, lock, and post-divider and leaves the
running shared PLL untouched. Long-sleep verification is pending.

The release records a separate 22-event wake history. On a terminal
handoff or early data failure it uses Atmosphère's reboot-to-fatal writer
with reason `DD200066`. The first command failure is recorded before
retrying. A recovered failure remains visible in a later manual snapshot.
The first eight ordinary data commands can retry through a refreshed ADMA2
table and then SDMA if command cleanup succeeds. A data CRC error goes
directly to the normal retune and verification path. Report `2e81f67`
showed three failures at tap 33 with 11 blocks remaining in both DMA modes,
after the clock had already recovered. A terminal wake error is captured
after recovery is exhausted. Verification and prefetch commands do not
consume the wake retry window. A submitted write is excluded from replay
because the card may already have changed data.

The read-ahead-only variant adds `EMUMMC_DDR200_ADMA_READAHEAD_ONLY`.
The timing variant adds `EMUMMC_DDR200_MATRIX` and
`EMUMMC_DDR200_DLL_DIAG`. Its v27 report captures five quiet sweeps and
eight stream sweeps per arm. It runs the no-DLL arm first, then calibrates
with a 10 ms deadline and repeats the same 64 MiB read workload if the
controller signaled calibration activity. A DDR200 reassertion schedules
a fresh comparison. The experiment restores the writable control registers.
The internal DLL delay is hardware state and its restoration is unverified.

Stock Hekate reads a single fixed KIPM path. The bundled Hekate patch adds
`ddr200_kipm=` for the two diagnostic entries. Its update build uses one
higher release byte so an existing Hekate payload can load it from
`bootloader/update.bin`.
